PROMPT B – Nihongo-based Journey build prompt (main prompt for non-Latin scripts)

Which prompt is this? This is PROMPT B, reverse-engineered from Nihongo Journey v2.5.0, with German Journey's architecture. Use it as the main prompt for non-Latin scripts (Korean, Chinese, Arabic, Hindi, Greek, Russian, Hebrew, Thai …). Use PROMPT A (German-based) as its companion for the exact data model, checked IPA for every word form, the accuracy pipeline and the word-box layout. For Latin-script languages, use PROMPT A as the main prompt and this one as the companion. See README - WHICH PROMPT TO USE.md.

Part 2 — The prompt (copy from here)

A. Goal

Build [APP NAME], a structured, local-first, 90-day [LANGUAGE] course for English speakers. It takes learners from zero to solid A1 and core A2, or the language's equivalent (JLPT N5/N4, HSK 1–2, TORFL A1/A2). Learners study 15, 30 or 45 minutes a day. One Expo / React Native codebase serves Android, iOS and the web.

  • Build it in [FOLDER], in a private GitHub repo [REPO].
  • Copy the Journey base from Nihongo Journey (CLAUDE FOR LANGUAGE\NIHONGO, the most complete reference).
  • Use German Journey (CLAUDE FOR LANGUAGE\german-journey) for its architecture document and its Latin-script solutions: gender colours and the respelling guide.
  • Read both apps; never edit them.

The app must be accurate, honest and beautiful, and look exactly like the other Journey apps, so a learner who knows one knows them all. Only the language, the accent colour and the content differ.

B. Honesty rules (never break)

  • No certificates and no guaranteed level. The About page lists the known limitations.
  • No fake test results and no fake approvals. Content status is auto-checked or needs-review. approved needs a named human reviewer, and the validator enforces this.
  • Audio is device text-to-speech, and the app says so: "computer-generated voice, not a native-speaker recording".
  • Report results faithfully. Never say a push, deploy, build or test passed unless it did. If something was skipped, say so.

The rest of the architecture:

  • SRS: SM-2 style and deterministic. Learning steps 1 min / 10 min, graduation 1 day, ease 2.5 (minimum 1.3), "mastered" at 21+ days.
  • Unlocking: each day needs the previous day. Week 1 day 1 also needs the previous week's test at 80%. Invalid days are skipped, so they never trap a learner. "Unlock all chapters" opens everything, per learner.
  • Accessibility:
    • every control has a role and a label
    • touch targets are at least 44 px
    • text size 90–150%
    • light, dark and high-contrast themes
    • foreign text tagged with lang on the web

F. Language pack, readings and transliteration (the language-specific core)

src/lang/[CODE]/tap.ts exports:

  • SCRIPT_RE / hasScript
  • tapTokens(text, style)
  • wordToken(text, reading, en?, vocab?, style)
  • syllables(reading, style)
  • exampleFor
  • meaningOf
  • phraseMeaning
  • splitRuns / japaneseRuns-style run splitting

Meaning chain, in order:

  1. The hand-written glossary (wins for ambiguous words).
  2. Curated sentence segment glosses.
  3. The course vocabulary.
  4. The analysed layer's dictionary form for conjugated words ("eat (polite past)").
  5. Numbers and counters (number → English, number+counter → "3 small animals", ordinals "the 2nd").
  6. Single-character data (kanji lab).
  7. The 5,000-word dictionary, used only when the match is unambiguous.

A compound is never glossed by one of its parts (牛丼 is not "cow"). If its meaning is unknown, it becomes a hand-written entry.

Readings layer (essential for non-Latin scripts; strongly recommended for every language), built offline by scripts/build-readings.ts into content/readings/readings.json:

  • Collect texts. Every foreign text in the content goes in: whole strings without Latin letters, every foreign run inside English text, and kana/reading fields.
  • Split and read. The analyser splits each text into learner-level words and gives each word its reading in context:
    • a verb or adjective keeps its endings
    • noun + light verb (する) is one word, flagged for a romaji split
    • number + counter is one word, read by the counter engine (三匹 さんびき, 六本 ろっぽん, 7時 しちじ)
  • Flags per word: p particle, v dictionary-form verb, s<n> noun+light-verb split, plus the base form (for meanings).
  • Reading priority:
    1. a FIXED_READINGS table for words the analyser gets wrong
    2. the counter engine
    3. a whole course word
    4. the dictionary reading for all-kanji compounds
    5. the course reading of a conjugated course verb
    6. the analyser Then context rules for known ambiguities (Japanese examples: 雨が降ります ふ; 本を開く ひら / ドアが開く あ; 何 before です なん; 〜中 ちゅう/じゅう; 来ない こ; 十分 after 歩いて じゅっぷん; noun + はいりません = は + いります).
  • Never guess. A lone character with no context gets no reading rather than a guess. A reading that contains script characters is rejected.
  • Text in one script only (kana-only, or any text the analyser mis-splits) uses a course-knowledge segmenter: a best-path search over every reading the course has already checked.
    • What it searches: vocabulary, all curated segment readings, glossary words, the dictionary, every engine conjugation, numbers and counters, particles and endings.
    • Its costs:
      • two nouns side by side +1.5
      • a particle at the very start +3
      • a one-sound word +2
      • an unknown chunk (place names) 3.2+, more if it swallows a particle
      • a stand-alone verb ending 2
    • Runs of a second script (katakana loanwords) are single words.
  • Multi-word sentence segments. Curated segments that are several words are split for romaji, but only when the words' readings add up exactly to the segment's checked reading. Curated morpheme parts win.
  • When to rebuild: run npm run readings:build then npm run glossary:auto after any content change.

Transliteration rules:

  • Non-Latin scripts use one standard romanisation (Japanese: modified Hepburn with macrons).
  • Latin scripts get an English-letter respelling with stressed syllables in CAPITALS, plus a legend (German).
  • Join rules (joinRomaji): a trailing geminate mark doubles the next consonant (tanoshikatta).
  • Textbook spacing (normaliseRomaji):
    • te-form + auxiliary apart (tabete imasu, matte kudasai)
    • desu ka
    • tai desu
    • n desu ga
    • nakereba narimasen
    • noun + light verb apart, from the course's own light-verb nouns (benkyō shimasu)
    • names capitalised
    • every sentence capitalised
    • a lone geminate dropped (えっ → e)
  • Particles and endings:
    • Particles are read as said (は → wa, へ → e, を → o, には → ni wa, ては → te wa).
    • A lone kana named as a sound reads as written (は = ha).
    • Grammatical endings that a glossary lists as separate pieces attach to their word in the romaji line (iki + tai → ikitai).
  • Regression tests: add one for every engine bug found (Nihongo: src/lang/ja/__tests__/romaji-audit-test.ts).

Engines (pure and tested): transliteration, numbers (cardinals, ordinals, prices, time, dates, years, phone, words → digits), counters with an English column, conjugation and grammar tables, answer matching, quiz, SRS and progress. For Latin scripts, add a rule-based sentence analyser for the validator (German: agreement, V2, case).

G. Curriculum

  • Structure: 90 days in 13 weekly modules and 7 phases. Levels 0–9 inside the 90 days and 10–12 as an outlined extension.
  • Weekly checkpoint: each week ends with a test; pass at 80% to open the next week. The app's default pass mark is 0.8, and every lesson text must say 80% (a setting can change it).
  • Week: an English title, a foreign heading (with transliteration chips) and a topic list with no repeats across weeks.
  • Day: fields title, titleJp-style foreign heading, emoji, summary, measurable objectives (🎯), newWords, grammar ids, pronunciation topic ids, analysed sentences, a dialogue, a reading, practice, review words, a quiz and completion text.

H. The day chapter (the same format every day; mirrors German Journey)

# Page Content
1 Start caption "DAY · WEEK · PHASE · LEVEL"; emoji + bold title; GlossLine of the foreign title; summary; a card "Today you will be able to…" with 🎯 bullets; a 📖 card with the day's intro text; the real-life photo card with its story; new characters (script languages); a counts line "N new words · M example sentences · K quiz questions · Complete the quiz with 80% to finish the day."; Begin
2 Pronunciation, every day The sound of the day. It is the lesson's own topic if it has one; otherwise it is chosen from the sounds the day's own words contain, rotating so topics don't repeat, with pitch/intonation topics using the lab's checked examples. It shows the title, category and IPA badges, the tip, a diagram, cards for today's words with the sound's letters coloured (plus transliteration, meaning and audio), the most common error, "Open in the Pronunciation Lab" and Say it yourself.
3 Script pages (non-Latin) new letters and characters with stroke animation
4 New words (N) One page, a card per word: photo or emoji tile, the word coloured by type (Latin languages with gender: by gender — der/die/das), reading, transliteration, meaning, key forms (verb group + polite + te-form; adjective negative/past; noun counter or plural), badges, example with audio, 💡 note, and a colour legend
5 Grammar, every day "NEW GRAMMAR", or "REVIEW — first taught on day N" for earlier rules (shorter). It shows the pattern, summary card, formula, explanation, table and a 📘 link. If the day has no grammar step, it uses the rules its sentences use.
6 Sentences All of the day's sentences on one page, each word in a box with a role-colour underline, plus grammar links

Every button says "Next: ", and every page caption shows "PAGE NAME · n / total".

I. Dialogue standard (measure it; don't guess)

  • Length: 12–16 lines per day. Days 1–7 may use 10–12.
  • Density: words per line must meet German Journey's level for the stage. Measure with scripts/audit/dialogue-stats.py, which counts English words per line.
Days Target (English words / line)
1–15 ≥ 6.5
16–30 ≥ 7.5
31–45 ≥ 9
46–60 ≥ 9
61–75 ≥ 9.5
76–90 ≥ 10.5

No more than 2 lines of 3 words or fewer. - Each line is a complete, natural thought (greeting + question, answer + reason, thanks + follow-up). Each dialogue tells one coherent story that fits its title and the lesson. Never write fragments like "Oh — teacher, snow!"; write "Oh, look, teacher! It's snowing again!" - Language: use the day's new words and grammar. Simple words beyond the syllabus are fine if every segment is glossed. Keep the register: polite by default, casual only in casual dialogues, keigo only where taught. - Consistency: keep facts consistent with the day's quizzes and listening questions (prices, change, times, names), and keep story continuity across days. Keep the ids of lines you keep; new ids are unused. - Review: a separate reviewer reads every new line before release.

J. Content rules

  • All content is JSON in content/, validated by zod plus language checks: npm run content:validate must show errors 0. Content that fails is hidden, never shown.
  • Every foreign string has an English meaning for every word. src/content/gloss-gaps.ts and gloss-coverage-test fail the build on a single gap.
    • Names say "(first name)" / "(surname)" and places say what they are.
    • Deliberately wrong forms are labelled "(wrong — correct: …)".
    • Hand corrections of the auto glossary go in a hand file that overrides auto.json.
  • Curated sentences:
    • segments with t, r (reading for every script character and digit), pos, gloss, fn for particles, and base/form/parts for conjugated words
    • segments join exactly to the text
    • a literal translation, alternatives, common mistakes with "why", grammar ids
    • a speak override when TTS misreads
  • Vocabulary: word, reading, part of speech, verb group or gender/plural, forms, IPA where checked, English, an example with translation, topic, level, an emoji or photo, and notes.
  • Editing: edit lesson JSON as text. Never re-serialise whole files, because that hides the real change.

N. Accuracy process (before every release; the Nihongo v2.5 method)

  1. Automatic checks: validator errors 0, gloss gaps 0, regression tests and a full-sentence romaji scan (scripts/audit/scan.ts).
  2. Export as shown. scripts/audit/audit-dump.ts exports every part (lessons by 15 days, grammar, vocab, kanji/script, glossary, auto glossary, scenarios/culture/placards/real-life) exactly as learners see it, romaji included. chunk.py splits the export into chunks of about 450 KB.
  3. Two independent reviewers per chunk. They share a brief (REVIEW_BRIEF.md) and write a JSON findings file: file, where, current, problem, category (grammar, reading, romaji, translation, gloss, fact, engine), severity, fix. Systematic romaji problems are reported once, as "engine".
  4. A third reconciler per area:
    • Fixes both reviewers agree on are applied.
    • Single-reviewer findings are judged, and applied only if real.
    • Engine findings are checked against the current output (rt.ts for any text, sr.ts for a sentence id); the engine is fixed in code, with a regression test, never patched in content.
    • Every decision is recorded.
  5. Rebuild and re-check: readings:build → glossary:auto → validator → gloss gaps 0 → npm run check → e2e.
  6. Waves: run reviewers in waves of 8–10 agents. Re-export after big engine changes so reviewers don't report issues that are already fixed.

Q. Security and git

  • Never commit .env files, keys, certificates, store credentials, recordings or learner data.

R. Owner's standing preferences (from the German and Nihongo builds)

Reporting

  • The clickable live web link goes at the top of every final report.
  • Always push to GitHub after changes, and always produce the four builds plus the source in a new version folder.
  • Report in plain English: what changed, how it was checked, the links and the files. Explain why when something differs from the reference. Ask only when a decision is genuinely the owner's.

Format

  • The same format across all Journey apps. Compare with German Journey page by page when asked. "Formatting only" means change nothing else.

Readings and tap boxes

  • Every foreign heading has transliteration, word chips with meanings, and audio.
  • Every foreign word anywhere can be tapped, heard and understood. Read aloud and highlight must match.
  • The word box never sends the learner to another page, and never stretches a table cell.
  • Words are cards, not loose rows. Objects use real photos (or emoji tiles), never childish pictures.

Lessons

  • Day chapters follow section H exactly: page 2 is always Pronunciation, a grammar page every day, the photo on the start page.
  • Dialogues are long and dense (section I), natural and sensible.
  • Lesson objectives keep 🎯.

Accuracy

  • Grammar, transliteration and translation are checked by multiple AI reviewers who cross-check each other, before a release.

S. Pitfalls already met (avoid them)

  • Romaji from an analyser that guesses. Dictionary-only greedy splitting gave "toki ni okimasu" for 7時に, "sanhiki", "hairimasen" and "ha" for は. Use the readings layer (F) from the start.
  • Analysers fail on one-script text. kuromoji split きょうはそら… into き + …; use the course-knowledge segmenter.
  • A whole-text fallback that is too eager hides good splits. Fall back only when no split exists.
  • Python heredocs eat backslashes in regexes. Write patch scripts to files, and use assert on every replacement so a silent non-match is caught.
  • In JS template strings \s becomes s and \b becomes a backspace. Write \\s and \\b.
  • Agents share the scratchpad. Give each agent its own subfolder.
  • Session limits. Too many parallel agents stop together. Resume each with a short message; their work is kept.
  • Dumps can mislead. An export that joins words differently from the app makes reviewers report non-issues. Make the export use the app's own functions.
  • Single-segment phrases (そうですか as one segment) need the splitter or the normaliser, or their romaji fuses.
